# For-Julian summary

Overall: **FAIL for unrestricted use with untrusted inputs; a restricted deployment needs fixes and review.**
The checked source is the requested release; Hermes was never installed, built, imported, or run for this audit.
The local dashboard gives its control token to local callers; another local process can use it.
Turning off borrowed logins protects the normal Claude/Codex discovery paths, but is not a universal credential-store lockout.
GitHub CLI login discovery remains enabled independently.
The reported `eval` command bypass has a detection rule now; the unmarked batch/noninteractive approval gap is not fully closed.
“Unattended deny” does not override an active API approval bridge or every approval bypass.
Desktop link previews can reach private networks; image saving still has an uncapped download path.
The dependency scan found advisory matches in 21 locked package/version pairs, including Electron and optional HTTPX2 dependencies.
Updates preserve local changes in common cases, but ordinary update settings do not enforce an immutable audited version.
Recommendation: keep this release constrained until the desktop fetchers and unattended execution boundary are fixed; use independent logins and reviewed, pinned releases.

## 2. Credential adoption and writes — CONCERNS

**Answer: `auth.adopt_external_logins: false` does not fully disable OS credential-store reads and writes across Hermes.** It is a narrow borrowed-Claude/Codex policy, not a process sandbox.

- **Direct, ordinary Claude flow:** `agent/credential_sources.py:32` defaults adoption to true; unreadable configuration returns true, and values are coerced with `bool(...)`. Use a real YAML boolean false, not the string `"false"`. `agent/anthropic_credentials.py:351` checks the flag before reading either Claude Code's credential file or macOS Keychain. `agent/credential_pool.py:2574` also gates the seed and prunes persisted `claude_code` rows when disabled. This is meaningful protection for a newly loaded pool under readable configuration.
- **Direct, writes exist:** borrowed Claude refresh can update the external credential file and mirror the consumed token's replacement into an existing matching Keychain item: `agent/anthropic_credentials.py:535`, `agent/anthropic_credentials.py:574`. It does not blindly create or overwrite an unrelated Keychain login. Nevertheless, the writer itself has no adoption-policy check. Pool refresh/persistence at `agent/credential_pool.py:1628` and `agent/credential_pool.py:1647` likewise does not recheck the flag. The fallback refresher reads fresh credentials but can still use its caller-supplied old refresh token (`agent/anthropic_credentials.py:475`, `agent/anthropic_credentials.py:484`). **Inference:** changing the flag while a process already holds a borrowed entry is not a guaranteed immediate revocation of all refresh/write capability. No such race was executed.
- **Direct, Codex:** automatic recovery checks the flag before importing (`hermes_cli/auth_codex.py:217`). The import reader reads the external CLI file and never writes it (`hermes_cli/auth_codex.py:563`); Hermes token persistence uses its own auth state (`hermes_cli/auth_codex.py:174`). Explicit interactive login still reads and offers import regardless of the flag (`hermes_cli/auth_codex.py:950`). Accepting import copies the existing token family; code does not obtain a new independent grant in that branch. The reassuring independence message at `hermes_cli/auth_codex.py:966` should not be treated as proof of token independence. Previously imported tokens are not automatically made independent by disabling future adoption.
- **Direct, GitHub exception:** Copilot calls `resolve_copilot_token()` without this adoption gate (`agent/credential_pool.py:2654`). That resolver falls back to `gh auth token` (`hermes_cli/copilot_auth.py:72`, `hermes_cli/copilot_auth.py:129`). The skills hub and general GitHub helpers have additional independent paths (`tools/skills_hub_github.py:118`, `hermes_cli/github_api.py:42`, `hermes_cli/git_credentials.py:69`). `gh` may read its OS credential store. Explicit source suppression exists, but the Claude/Codex flag is not that suppression mechanism. Ambient Copilot discovery avoids the network token exchange until the provider is explicitly configured (`agent/credential_pool.py:2679`); local discovery still occurs.

Recommendation: independent OAuth grants, a fresh process/pool after policy changes, readable boolean configuration, and an OS account/process boundary if the requirement is “cannot touch another application's credentials.” These are recommendations only; no credentials or configuration were inspected or changed.

## 3. Auth gates — CONCERNS

**Dashboard loopback boundary: direct FAIL against isolation from other local processes.** The session token is random or supplied by the desktop (`hermes_cli/web_server.py:328`). In ungated mode, SPA HTML injects it (`hermes_cli/web_server_dashboard.py:140`, `hermes_cli/web_server_dashboard.py:155`); headless mode deliberately serves it at exact `GET /` (`hermes_cli/web_server_dashboard.py:110`). The token is accepted in a dedicated header or Bearer auth (`hermes_cli/web_server.py:416`); sensitive endpoints use it (`hermes_cli/web_server.py:442`, `hermes_cli/web_server.py:660`). Therefore a local HTTP client that can reach an ungated listener can read the page, extract the token, and authenticate. This is source-derived control access, not a live request to a running service. It does not require the client to share a browser cookie jar.

CORS and Host validation protect different boundaries: loopback origins only (`hermes_cli/web_server.py:401`) and explicit Host validation (`hermes_cli/web_server.py:459`, `hermes_cli/web_server.py:590`). They do not authenticate a native local client, and a browser page served on another allowed localhost port may also read under this CORS policy, subject to browser restrictions. Remote-browser exploitation was not tested.

**Public/remote binding: static PASS for gate selection.** Non-loopback binds and a declared non-loopback public URL require the auth gate; the legacy insecure switch is ignored (`hermes_cli/web_server.py:481`, `hermes_cli/web_server.py:491`, `hermes_cli/web_server.py:1110`). Desktop-owned loopback exceptions remain. Gated HTML omits the bearer token. A reverse proxy left undeclared can still expose an ungated loopback backend; configure/authenticate the actual public entry point rather than assuming loopback alone supplies login security.

**API server: static PASS on normal startup.** Missing/weak keys are refused, including loopback; minimum usable-secret check is 16 characters (`gateway/platforms/api_server.py:4243`, `gateway/platforms/api_server.py:4280`). Bearer comparison is timing-safe bytes (`gateway/platforms/api_server.py:1454`). Caveat: the check helper's no-key/default-profile branch returns success, relying on startup admission; manually embedding/bypassing `connect()` must enforce the guard too. Named profiles fail closed.

**Webhook: CONCERNS.** Startup requires a secret; `INSECURE_NO_AUTH` is restricted to loopback (`gateway/platforms/webhook.py:199`). GitHub/Linear HMAC-SHA256 and GitLab token checks compare safely (`gateway/platforms/webhook.py:724`). Generic V2 signs timestamp plus raw body, rejects stale/missing timestamps, and does not downgrade to V1 (`gateway/platforms/webhook.py:731`); Svix has timestamp validation (`gateway/platforms/webhook.py:130`). Legacy generic V1 signs only the body and remains accepted with an explicit replay warning (`gateway/platforms/webhook.py:746`). Prefer timestamped V2 plus replay/idempotency controls appropriate to the sender; a valid HMAC alone does not guarantee freshness.

## 4. Command gate and named CVEs — FAIL

**Direct positives:** host-style command checks run the hardline floor before YOLO, approval-off and permanent allowlists (`tools/approval.py:1052`, `tools/approval.py:1159`). The blocklist covers root/home/system deletion, filesystem formatting, raw-device writes, fork bombs, global kills and reboot/shutdown (`tools/approval_detection.py:88`). It is a syntactic guard, not a complete sandbox. The container-skip branch precedes that floor for backends classified as isolated; Docker with host access keeps checks (`tools/approval.py:1024`, `tools/approval.py:1166`). Internal `force` execution also bypasses the terminal gate (`tools/terminal_tool.py:909`); this audit does not assert that parameter is directly model-exposed.

**CVE-2026-9350: not fully fixed in the unknown/batch-context threat model.** The [CNA record](https://cveawg.mitre.org/api/cve/CVE-2026-9350) identifies the batch approval fallback; the [reporter's original analysis](https://gist.github.com/YLChen-007/22cada4c9060f5123dde6185135ae3ab) explains the missing interactive markers. Current `check_all_command_guards` still returns approved when none of CLI/gateway/ask is present and no recognized unattended context blocks (`tools/approval.py:1184`). Only single-query, cron and three named programmatic platforms populate the unattended list (`tools/approval.py:618`; `tools/approval_context.py:134`). Batch defaults to a local terminal and passes `platform="batch"` to `AIAgent`, but does not set these approval markers (`batch_runner.py:189`, `batch_runner.py:245`, `batch_runner.py:454`). The approval platform reader uses session context/environment, not that object field (`tools/approval_context.py:121`). The original root-delete example now hits the hardline floor, but non-hardline dangerous commands can still take the auto-approved fallback. This is a static call-path conclusion, not an executed batch exploit.

**CVE-2026-9367: the specifically reported spelling is covered, not a universal fix claim.** The [CNA record](https://cveawg.mitre.org/api/cve/CVE-2026-9367) and [original report](https://gist.github.com/YLChen-007/75fb10319693e86106ced2ef3a472c80) describe evaluation of downloaded content via command substitution. `tools/approval_detection.py:294` now includes pipe-to-shell, process substitution, and `eval`/`source`/dot with download command substitution. In an attended, non-bypassed context this becomes an approval finding (`tools/approval.py:1204`). The generic unattended fallback above can still skip that detection. No exhaustive shell-obfuscation proof or dynamic CVE regression was run.

**`approvals.unattended_mode: deny` is conditional, not an execution ban.** With no human/ask bridge it denies detected dangerous commands; ordinary commands still run, permanent approvals can exempt patterns, and scanner-import behavior depends on `tirith_fail_open` (`tools/approval.py:637`; `tools/approval_context.py:308`). YOLO/off and the permanent command allowlist are evaluated earlier (`tools/approval.py:1178`). The `/v1/runs` ask bridge is deliberately retained (`tools/approval.py:934`), and the unattended-deny branch runs only when `is_ask` is false (`tools/approval.py:1187`). Gateway startup sets `HERMES_EXEC_ASK=1` (`gateway/run.py:5770`); run launch registers a notifier (`gateway/platforms/api_server_runs.py:824`) and emits `approval.request` (`gateway/platforms/api_server_runs.py:850`). The response endpoint authenticates run ownership/approve permission; room-scoped grants are restricted to once/deny (`gateway/platforms/api_server_runs.py:1165`). An authorized API approver can approve a flagged action despite unattended deny. No listener/timeout normally leaves it unapproved; the bridge is not evidence of anonymous auto-execution.

Recommendation: default unknown execution contexts to deny flagged actions, explicitly classify batch, and separate “human approval available” from an immutable policy prohibition. Keep run-dispatch grants distinct from approve grants. Rely on an actual restricted OS/container boundary for untrusted execution.

## 5. Desktop Electron — FAIL

**Isolation settings: direct positive.** Main chat windows use `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false` (`apps/desktop/electron/session-windows.ts:49`). Hidden title windows use the same settings and `webSecurity: true`, with JavaScript enabled (`apps/desktop/electron/link-title-window.ts:8`). Popup denial and title-session download cancellation exist (`apps/desktop/electron/link-title-window.ts:34`, `apps/desktop/electron/link-title-window.ts:53`). Main-window navigation is constrained and routed externally (`apps/desktop/electron/main.ts:13177`). These settings reduce renderer escape risk but do not remove authority exposed through preload IPC.

**CVE-2026-85106 relevance: private-network title fetch remains.** The [CNA record](https://cveawg.mitre.org/api/cve/CVE-2026-85106) names the older artifact component. At this commit the common link helper rejects several schemes and exactly localhost/127.0.0.1/0.0.0.0/IPv6 loopback (`apps/desktop/src/lib/external-link.tsx:25`, `apps/desktop/src/lib/external-link.tsx:127`). It does not reject RFC1918/link-local addresses, other loopback addresses, or public names resolving/redirecting to private addresses. The preload forwards the URL to main (`apps/desktop/electron/preload.ts:410`; IPC at `apps/desktop/electron/main.ts:17629`). Main's cache-key parsing is not a destination policy (`apps/desktop/electron/main.ts:5327`): it calls curl with redirects, then possibly a hidden renderer (`apps/desktop/electron/main.ts:5368`, `apps/desktop/electron/main.ts:5559`). No resolved-IP/redirect destination check was found in these paths. **Inference:** a rendered private-address link or an attacker-controlled public URL redirect can cause a request from the desktop's network position. Title bytes may expose returned page titles; arbitrary response-body exfiltration was not proven. Curl has time/byte budgets (`apps/desktop/electron/main.ts:5291`, `apps/desktop/electron/main.ts:5413`), which do not fix SSRF.

**CVE-2026-85107 relevance: removed copy entry point, surviving save entry point.** The [updated CNA record](https://cveawg.mitre.org/api/cve/CVE-2026-85107) says `copyImageFromUrl` was removed and copy now uses `event.sender.copyImageAt`; this matches `apps/desktop/electron/main.ts:17131`. However `resourceBufferFromUrl` still exists (`apps/desktop/electron/main.ts:5750`) and is called by `saveImageFromUrl` before showing the save dialog (`apps/desktop/electron/main.ts:5803`). HTTP response chunks accumulate without a byte cap or request timeout (`apps/desktop/electron/main.ts:5776`); data URLs are decoded into a full buffer, and allowed file reads are full-buffer too. The save IPC handler remains reachable (`apps/desktop/electron/main.ts:17107`; `apps/desktop/electron/preload.ts:348`), with context-menu and download-button callers (`apps/desktop/src/app/context-menu/app-context-menu.tsx:276`; `apps/desktop/src/hooks/use-image-download.ts:88`). **Inference:** saving a large/endless remote image can exhaust memory or hold resources. Do not report the vulnerability class as closed simply because the old copy handler disappeared. No crash/resource-exhaustion test was performed.

Remediation: validate scheme, resolve and reject private/loopback/link-local destinations in main, revalidate each redirect and prevent DNS rebinding; stream image downloads with enforced byte/time limits before allocation. Decide explicitly whether local-resource links are permitted and require a separate trusted action if so. Upgrade/review Electron as part of the same change (area 8).

## 6. Skills, plugins and Curator — CONCERNS

**Skills installation: direct positive, not a proof that content is safe.** Downloads are quarantined/scanned and policy-evaluated before publication (`hermes_cli/skills_hub.py:719`). Ordinary CLI install asks for confirmation; force/skip-confirm paths exist (`hermes_cli/skills_hub.py:739`). The installer validates names/category/quarantine containment and refuses symlink/junction redirection (`tools/skills_hub_install.py:38`, `tools/skills_hub_install.py:143`, `tools/skills_hub_install.py:175`). Managed target is the profile's `skills/` tree with `.hub` provenance/lock/audit data. Regex/advisory content scanning cannot prove a skill free of malicious instructions. There is also a transactional concern: an existing target is removed before the later bundle symlink loop (`tools/skills_hub_install.py:160`, `tools/skills_hub_install.py:175`); assess failure/rollback behavior before relying on reinstall as lossless.

**Plugins:** clone into temporary staging; resolve an exact revision; constrain subdirectory/name; scan before publication; retain explicit revision pins and record provenance outside the plugin tree (`hermes_cli/plugins_cmd_install.py:284`, `hermes_cli/plugins_cmd_install.py:306`, `hermes_cli/plugins_cmd_install.py:319`, `hermes_cli/plugins_cmd_install.py:377`). Shared-environment Python dependencies have a consent gate; noninteractive install declines that preparation (`hermes_cli/plugins_cmd_install.py:84`). Plugins remain executable Python/Node extensions, not isolated data. Discovery includes bundled/user/project/entrypoint surfaces (`hermes_cli/plugins.py:1`); an enabled malicious plugin has the host process's privileges. Default automatic update application is false, while update checking is on (`hermes_cli/config_defaults.py:1702`). Reviewed catalog SHA trust is specific to the matching tree, not a blanket trust in every future revision.

**Curator is autonomous maintenance, not a generic plugin auto-installer.** It is enabled by default, defers first observation by an interval, and receives scheduled idle checks (`agent/curator.py:105`, `agent/curator.py:160`; `gateway/run.py:4622`, `gateway/run.py:4796`). It can transition/archive/consolidate/patch skills and rewrite affected cron skill references (`agent/curator.py:674`, `agent/curator.py:720`). Thus its write scope includes skill state/archive/backup/reports **and cron references**, not only Markdown. It snapshots for rollback (`agent/curator_backup.py:1`). The review agent has only the skills toolset, no terminal, and marks background-review origin (`agent/curator.py:1077`). Guards refuse pinned, external, builtin, bundled, hub-installed and non-agent-owned skills, failing closed when ownership cannot be established (`tools/skill_manager_guards.py:165`). Existing credential/provider selection determines any model traffic; this is not an offline-only deterministic maintenance path.

Recommendations: disable autonomous curation if skill immutability is required; pin approved plugin revisions; review their dependencies and executable code; treat scans as an input to approval. No plugin/skill/Curator operation was invoked.

## 7. Update path — CONCERNS

**Direct: normal local-change stashing is reasonably defensive.** The updater includes untracked files, records the new stash commit rather than trusting `stash@{0}`, verifies a stash was actually created, and aborts if changes were not saved (`hermes_cli/update_cmd_stash.py:76`, `hermes_cli/update_cmd_stash.py:98`). Applying conflicts preserves the stash and resets the post-update working tree; receipts record parked changes (`hermes_cli/update_cmd_stash.py:318`). Restored Python files get syntax/import checks before the corresponding stash is dropped (`hermes_cli/update_cmd_stash.py:366`). `--keep-stash` intentionally parks edits, including for desktop updates (`hermes_cli/subcommands/update.py:45`). This was read, not simulated by running the updater.

Limits: ignored files are not included by `--include-untracked`; pre-existing merge/index state can be changed; reset-on-conflict leaves edits recoverable in the stash rather than active. Concurrent unrelated edits are not proven safe. The explicit noninteractive `discard` setting drops the stash, so “updates always preserve all local edits” is false (`hermes_cli/update_cmd_stash.py:403`). Default is stash, with pre-update quick state backup (`hermes_cli/config_defaults.py:2331`, `hermes_cli/config_defaults.py:2335`).

**Pinning/review:** `--branch` selects a mutable branch, not an immutable audited commit (`hermes_cli/subcommands/update.py:52`). A clean parked branch can automatically switch to the update target by default (`hermes_cli/config_defaults.py:2340`). Merely disabling banners with `updates.check: false` does not prevent explicit updates (`hermes_cli/source_check.py:364`). A real commit-build install is recognized by its install stamp and refused in-place updates (`hermes_cli/update_contract.py:24`, `hermes_cli/update_contract.py:88`); image-managed installations have their own admission rules. Use a reviewed immutable commit/image/build and replace it only after reviewing the candidate diff and lockfiles. Keep plugin auto-apply disabled and pin plugins separately. This is a proposed release process, not a configuration change made by this audit. Do not forge an install stamp and assume that creates a secure immutable deployment.

## 8. Dependency audit — CONCERNS

**Actual network check, no Hermes execution:** independent standard-library scripts submitted locked public package names/versions to the same OSV querybatch API used by `hermes security audit` (`hermes_cli/security_audit.py:177`, `hermes_cli/security_audit.py:236`).
